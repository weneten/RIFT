# Linux deployment and verification

## Preflight before changing host networking

Run these checks from a disposable Linux VM first. Do not run the destructive parts of the integration harness on a production VPS.

1. Record `uname -a`, `uname -m`, `docker version`, `docker compose version`, `ip -V`, `wg --version`, `nft --version`, and `iptables --version`. Confirm the container target is supported (`linux/amd64` or `linux/arm64`).
2. Inspect current `ip -4 rule`, `ip -6 rule`, `ip -4 route show table all`, `ip -6 route show table all`, `nft list ruleset`, and (when installed) `iptables-save`/`ip6tables-save`. Save these outputs outside the production deployment state for comparison.
3. Check WireGuard on the actual host kernel in a temporary network namespace: `ip netns add rift-preflight`; `ip -n rift-preflight link add rift-probe type wireguard`; delete the namespace. A successful probe establishes that the kernel supports the interface in that namespace. A version string alone does not prove kernel configuration or module availability. If the distro ships WireGuard as a module, the host administrator may need to load/install it before the container starts; the image does not load kernel modules.
4. Run `sudo sh deploy/prepare-host` once on the host. It installs `/etc/sysctl.d/99-rift.conf` with `net.ipv4.ip_forward=1`, `net.ipv6.conf.all.forwarding=1`, and `net.ipv4.conf.default.rp_filter=2`, applies those values, and checks WireGuard in a temporary namespace. RIFT does not change the global sysctls: `/proc/sys` is often read-only in the container, and a container write would not survive reboot. `rp_filter=2` on `default` makes new interfaces, including `rift0`, inherit loose source validation. RIFT still sets loose mode on its own `rift0` when that file is writable. Do not set `net.ipv4.conf.all.rp_filter=0`. If fwmark routing rejects valid return traffic, evaluate `src_valid_mark=1` on exact interfaces in staging. Enabling IPv6 forwarding can change router-advertisement behavior; if the public NIC relies on RA, check its `accept_ra` setting.
5. Confirm the host SSH route and session remain stable, and confirm free UDP port 51820 and TCP port 8443. Open only the ports required by the deployment in cloud security groups. With `host_firewall = "auto"`, RIFT itself extends the UFW user chains (or, without UFW, any other firewall chain that drops by default) for UDP 51820, TCP 8443, TCP 8444 on `rift0` only, and forwarding between the public NIC and `rift0`. A separate UFW allow for each published port is unnecessary; traffic still has to match a RIFT grant. TCP 8444 is not opened on the public interface. If `host_firewall` is `off`, open those same paths manually. An accept in the RIFT table does not override a drop in another filter chain.
6. Render the Compose config with `docker compose config` in the RIFT directory (with the `.env`). On the agent, use `docker compose config --quiet`: full Compose config output contains the expanded enrollment token. Verify there is no `privileged`, no added `SYS_ADMIN`/`NET_RAW`, no Docker port publish in host mode, and no unexpected host path mount. `RIFT_PUBLIC_IPS` must list the actual public address(es), not documentation examples.
7. By default the server creates and persists its own CA, TLS certificate, and private keys in the RIFT state volume. The certificate SAN uses `RIFT_PUBLIC_ENDPOINT`; keep the state volume private and persistent. If using external TLS material, set all of `tls_cert`, `tls_key`, and `tls_ca` together, mount the files read-only, and verify the trust anchor matches the certificate chain.

The Compose file uses `network_mode: host`; the container shares the Linux host's network namespace. `CAP_NET_ADMIN` is therefore host-impacting. Docker may change forwarding sysctls and forwarding firewall policy when its bridge networking starts. Keep Docker's firewall integration enabled and do not edit or flush Docker-created rules. RIFT adds and deletes its own routes, policy rules, links, and nftables objects. With `host_firewall = "auto"` it also owns the `rift-host-in` and `rift-host-fwd` chains and their single jump from a UFW user chain or, without UFW, from a foreign chain that drops by default. Reserve distinct route table IDs, rule priorities, and packet marks for RIFT; do not take over the main/default tables or remove unrelated rules.

The image provides a Docker healthcheck for both server and agent, so monitoring tools such as Beszel can report the container's health. It runs `rift status` against the local admin socket every 30 seconds, with a 90-second startup grace period and three retries. An agent remains unhealthy while it has not enrolled. A successful check means the local status request succeeded; it does not guarantee that peers are online or that forwarded traffic works. Inspect `docker inspect --format '{{.State.Health.Status}}' rift-server` (or `rift-agent`) and use `rift status` for more detail. Rebuild or pull an image containing this healthcheck and recreate existing containers to activate it.

## Publish a home service with a name

The installed site commands (`rift add site`, `rift remove site`, `rift list sites`) use the helper `deploy/vps/rift-site`, which runs on the VPS host, outside the read-only RIFT container. It stores its state in `/var/lib/rift-site/sites.json`. One command allocates a listen port in `20000-20999`, adds a transparent `--ingress local` forward, and writes a site file for Traefik, Caddy, or Nginx, or creates a proxy host through the Nginx Proxy Manager API.

```sh
sudo rift add site node1 app.example 8081 traefik
sudo rift add site node1 app.example 8081 caddy
sudo rift add site node1 app.example 8081 nginx
sudo rift add site node1 app.example 8081 npm
sudo rift remove site app.example
```

Without a proxy word, the command uses the saved default (`traefik` until `sudo rift proxy caddy` or `sudo rift proxy nginx`). The chosen proxy must be the process listening on TCP 443. Otherwise the command exits before it creates a forward and names the proxy that does hold 443. It does not start a second proxy.

The home service must listen on the target port for the agent tunnel address, for example `0.0.0.0`. The proxy reaches the service through the VPS public address so prerouting DNAT still applies. Packets from the internet to the allocated high port are not forwarded. Traefik uses the existing certificate resolver. Caddy obtains the certificate itself. Nginx runs `certbot --nginx` when `certbot` is on the host; if it is missing, the site file is still written and the command says that TLS was not requested.

The first Traefik add, when Traefik's file provider is still a single file, copies that file to `/root/traefik/dynamic/ssh.yml`, switches the Compose service to `--providers.file.directory=/dynamic` with `--providers.file.watch=true`, and recreates that service. Docker-label routes are left as they are. Point DNS for the new name at the VPS public address.

## Rollout and rollback

1. Deploy the exact image and config to a disposable Linux VM with the same kernel family, Docker backend, and firewall manager as production.
2. Keep a separate working SSH session and a timed out-of-band recovery path. Capture the host's routes, policy rules, firewall rules, sysctls, and Docker network state before startup.
3. Start the server and one agent, then verify `rift status`, handshake state, and a test forward. Add more agents only after the first has survived restart.
4. For rollback, stop only the RIFT Compose project. An orderly stop removes RIFT-owned networking state; check logs for cleanup failures and compare host state against the saved baseline. A forced kill may leave state behind. Never use `nft flush ruleset`, `ip rule flush`, `iptables -F`, or a blanket route-table flush on a shared host.
5. Simulate termination during startup and after configuration has applied. After restart, verify the service reconciles only its owned objects and does not change the normal main-table route or SSH path. A network namespace teardown removes objects inside that namespace, but host-side veths/routes/rules require explicit ownership-aware cleanup.

Do not declare the host-network deployment safe from container-level tests alone. Host networking intentionally removes network-namespace isolation; a separate bridge/network-namespace design is preferable when the service can forward traffic without directly owning the host stack.

## Functional test matrix

Run `sudo env RIFT_NETNS_DISPOSABLE_VM=1 bash tests/netns/run.sh` on a disposable Ubuntu or Debian Linux host with root privileges, `iproute2`, `wireguard-tools`, `nftables`, `conntrack`, `openssl`, and the built RIFT server/agent binaries. It creates isolated namespaces and real WireGuard interfaces, a temporary bridge and NAT router, and removes them on exit. It must not run on a production host. The harness is expected to fail if a prerequisite or behavior is missing; it does not silently skip checks.

For the container runtime in bridge mode, run `sudo env RIFT_DOCKER_BRIDGE_VM=1 bash tests/docker/bridge-smoke.sh` on a disposable Linux VM with Docker Engine. This test builds the image, starts a server, one agent, and a separate client on an isolated dual-stack Docker bridge, then checks source-preserving IPv4/IPv6 TCP/UDP forwarding through a real WireGuard tunnel and the reply route back to the client. It uses only `CAP_NET_ADMIN`; it never enables host networking or publishes ports. It is not a substitute for host-network VPS testing.

The site helper's tests run anywhere with Python 3: `python3 -m unittest discover -s deploy/vps -p 'test_*.py'`. `python3 tests/proxies/run.py` needs Docker Engine; it renders sites with `--allow-from` through the helper's own functions, starts Traefik 3, Traefik 2, Caddy and Nginx on a throwaway Docker network next to a small backend, and checks that an allowed client gets 200 from the backend and any other client 403. It removes its containers and network on exit. Nginx Proxy Manager is not started; a plain Nginx runs its proxy host layout (the helper's advanced configuration at server level, NPM's ACME challenge location with `allow all`, then `location /`) and the test checks that the challenge path stays reachable for every list.

The Docker publishing integration test runs in a disposable Linux VM only: `sudo env RIFT_DOCKER_PUBLISHED_VM=1 bash tests/docker/published-port-e2e.sh`. It runs the agent in the host network namespace (matching the Compose host-network agent), while the VPS and client use isolated network namespaces and the destination is a real Docker bridge container reached through four Docker `-p` mappings. It verifies the original IPv4/IPv6 client address on TCP and UDP replies. The test temporarily enables host forwarding and loose default reverse-path filtering, records and restores those three sysctls on exit, refuses an existing `rift0`, `inet rift` table, rule priority 11000, or nonempty route table 51888, and cleans only its test objects. Run it only on a disposable runner; it exercises Docker's host firewall integration.

That same published-port test includes two application checks. Its SFTP image is built only for testing and creates ephemeral SSH host keys; the client obtains the server public key from the container, pins it in `known_hosts`, requires strict host-key verification, uploads/downloads a file over IPv4 and IPv6, compares SHA-256 hashes, and checks `sshd` logs for the original client address. Its official `traefik:v3` test container serves HTTPS on the forwarded port, routes through the file provider to a small HTTP backend, and writes JSON access logs. A short-lived test CA signs a certificate with the VPS test VIPs as IP SANs; the client verifies it with `curl --cacert`, and the test checks each log's `ClientHost` against the original IPv4/IPv6 client address. The test does not configure PROXY protocol. These application checks run in the `docker-bridge` CI job; check that job's result for a given commit before treating them as passed.

| Area | Evidence |
|---|---|

| TCP and UDP | Echo service succeeds for each family/protocol and returns the observed source address; the harness does not capture packets or independently verify server-side peer logs. |
| Docker published backend | Disposable-host test sends distinct client IPv4/IPv6 TCP/UDP flows through a host-network agent to a Docker `-p` bridge backend and checks the echo source and return path. |
| SFTP | The same disposable-host test requires strict pinned SSH host keys, tests upload and download hashes for IPv4 and IPv6 clients, and checks original client addresses in `sshd` logs. |
| HTTPS / Traefik | The test verifies an IP-SAN certificate against its temporary CA using `curl --cacert`, forwards requests through Traefik v3's file provider to an HTTP backend, and checks JSON `ClientHost` values for both client families. PROXY protocol is not enabled. |
| Proxy on the VPS itself | The namespace harness adds local-ingress forwards (IPv4 TCP and UDP, IPv6 TCP) and connects to them from the VPS namespace itself, as Caddy or Nginx from the distribution do: the agent's echo answers with the VPS address, the forwards appear in the `output_nat` chain, a client from the internet gets no answer, and the chain is gone after the last such forward. Nginx from Ubuntu 24.04 with a site file from the helper was checked by hand through the output translation in two namespaces. |
| Panel over HTTPS | Unit tests: with `RIFT_WEBPANEL_CONTROL=public` a request through a listed proxy over HTTPS may change things, over plain HTTP or from an unlisted source it may not, the private paths stay, and with `private` the same proxy request is read-only; UFW admits the proxy network to the tunnel address only. Not run with a real RIFT server or a real certificate. |
| `deploy/setup-proxy` | Not run in CI. The script refuses ports held by another container. `--migrate` moved two sites (one with `--allow-from`) from Caddy to Nginx Proxy Manager, from there to Traefik and, after the old proxy was stopped by hand, back to Caddy; each time both answered through the new proxy with their forwards unchanged and the old files removed. A Caddy that failed to validate made the script start Traefik again, with the sites unchanged. Real Let's Encrypt certificates were not issued (no public domain). |
| Source allow-lists | The namespace harness adds `--allow-from` forwards for transparent IPv4 TCP and UDP, transparent IPv6 TCP and a translated IPv4-to-IPv6 TCP forward. An allowed client reaches each one, a second client gets no answer, an unrestricted forward of the same agent still answers that client, the source set appears in the server's DNAT chain, and a list without an address of the listener's family is refused. `tests/proxies/run.py` runs the site `--allow-from` configuration in real Traefik 2 and 3, Caddy and Nginx (200 for the allowed client, 403 otherwise), plus Nginx Proxy Manager's proxy host layout in plain Nginx; NPM itself is not started. |
| Policy routing | Marked client traffic selects the RIFT table and WireGuard; unmarked traffic uses the same baseline route and public egress before/after. The WireGuard UDP endpoint remains on the underlay. |
| Endpoint/NAT change | Change the remote endpoint IPv4 and the translated UDP source port in a NAT namespace; prove handshake and bidirectional traffic recover without changing the VPS default route. |
| Three agents | Enroll three agents and exercise each agent's independent public TCP/UDP forwards. |
| Agent isolation | Every agent runs a listener on the same target port that answers with the agent's name; IPv4 and IPv6, TCP and UDP forwards of each agent must be answered by that agent. Each agent's WireGuard peer on the server carries only its own tunnel addresses. Each agent then routes the other agents' tunnel addresses into the tunnel, as a compromised agent could, and must get no answer from them over IPv4/IPv6, TCP/UDP. |
| Coexistence | The namespace harness installs a separate Fail2ban-style nftables table on an agent with exact-client INPUT and FORWARD drops. It checks that the banned client's services fail, the other client and RIFT control state remain available, RIFT policy re-apply leaves the foreign table intact, and deleting the foreign table restores access. Separately, `rift add ban FORWARD_ID ADDRESS --ttl DURATION` sends a restricted ban request to the agent of that forward for an active translated forward; the namespace test checks source isolation and automatic TTL expiry. There is no explicit remove subcommand; expiry is time-based. |
| Crash/restart | Kill/restart an agent after apply and verify it restores saved forwarding policy. Kill the server with SIGKILL and restart it: its admin socket returns, unrelated nftables/IP rule state survives, forwarded IPv4/IPv6 TCP/UDP traffic works again and RIFT's policy rules exist only once. After an orderly stop, kill the server with SIGKILL again and again a little later in its start, until kills have landed between the start of its apply (enrollment endpoint open) and `RIFT server ready`; kill an agent as soon as its WireGuard interface exists (an agent logs no ready line, so its kill point is less exact); start both again and check forwarding, single RIFT rules and tables, unrelated state and the unmarked underlay path. |
| Cloud NAT | A second server has only a private address (`10.99.0.2`); a gateway namespace maps a public address 1:1 onto it, as Oracle Cloud, AWS and Google Cloud do. With `RIFT_ALLOW_PRIVATE_LISTENERS=true` (without it, the server refuses forwards on the private address; unit tests cover that rule), an agent behind another NAT enrolls through the public DNS name, dials the public address over WireGuard, and TCP/UDP forwards on the public address reach it with the client's own source address. This simulates the provider's NAT; it does not replace a test on a real cloud account. |
| Enrollment and TLS | The harness rejects wrong-CA TLS, replay of a consumed invitation and an invitation whose one-minute TTL has passed (no agent is created, `rift status` no longer lists it), and checks generated server private-key file permissions. Unit tests check the same expiry at the enrollment handler and that the invitation secret is not stored in plain text. |
| VPN device and names | A device namespace runs a real WireGuard client with the configuration from `rift vpn connect`. It reaches its granted port with its own VPN address and nothing else (another port, another agent). Another port on the same agent needs no new configuration and RIFT says so (`reimport` empty); a grant on a new agent does, RIFT names the device, and the old configuration does not reach the new agent. With `rift vpn names agent agent1 on` the device's DNS server becomes the server's tunnel address: `agent1.internal` resolves through the tunnel (case-insensitive), agents without names or without a grant do not exist, a second agent's names need no new configuration, and other names are relayed to a home DNS server on the device's DNS agent (`rift vpn dns`), asked by the server with the device's address as EDNS Client Subnet (the stand-in answers with that address, so the test sees it arrive). After `rift vpn names device phone off` the device gets a new configuration and the server no longer answers it. |
| Plain-text secrets | At the end the harness collects every invitation token (and its inner secret) and every private key from the state directories (WireGuard, TLS CA and server key). None may appear in any daemon log, in `rift status`, `list`, `show agent`, `logs`, `doctor` or `export` output, or in any state file other than the key's own file and `tls-bundle.json` (by design the durable source of the generated TLS keys); every key file and the bundle must be mode 0600. |

The bridge and published-port tests validate real client datapaths; neither proves production host-network safety or SSH continuity. The SFTP test validates a small file transfer and source logging, not large-transfer behavior or production key lifecycle. The Traefik test validates TLS termination, file-provider routing, and source logging, not reverse-proxy headers or production health checks. Also run staging tests for firewall backend compatibility, systemd/host reboot behavior, cloud security groups, and SSH continuity.

## Field checks on real hosts

Some release gates need real machines: a real cloud NAT, a host reboot, other firewalls next to RIFT, Proxmox LXC, and throughput. `deploy/field-check` collects the evidence; run it as root on the server and on every agent and send in the reports it writes (`rift-field-report-TIME.txt` in the current directory). It reads only, holds no keys, tokens or passwords (no `.env`, no key files), but does contain the host's addresses and agent names: read a report before sending it.

| Gate | What to do | What to send |
|---|---|---|
| Basics | `sudo sh deploy/field-check` on every host. | The report: container, restart policy, Docker at boot, WireGuard module, forwarding sysctls, firewalls, `rift status` and `rift doctor`. |
| Real cloud NAT | Install the server on a cloud VM whose public address is not on the interface (Oracle Cloud, AWS, Google Cloud), as in the README, then run the basic check there and on an agent, and test a forward from outside. | Both reports and whether the forward answered with the client's own address. |
| Host reboot | `sudo sh deploy/field-check --before-reboot`, reboot, `sudo sh deploy/field-check --after-reboot`. Do it for the server and for an agent. The policy rule exists on agents only. | The after-reboot report: it compares interface, nftables table, policy rule, forwards and agents with the reference and waits up to three minutes for RIFT to come back alone. An empty reference (RIFT not running) is a failure, a partial one a warning. |
| Firewalls | Run the basic check on hosts with UFW active, with firewalld, and on an Oracle Cloud image (its `REJECT` rule); test a forward and a VPN grant on each. | The reports (they list UFW, firewalld, iptables and nftables state) and which tests worked. |
| Proxmox LXC | Set up an agent in an LXC container as in the README section, then run the basic check inside it, before and after a reboot of the container. Restarting only the container is enough (the check notices it by the container's own init); rebooting the Proxmox host is the stricter test. | The reports. |
| Throughput | On the server: `sudo sh deploy/field-check --perf AGENT CLIENT_IP`. It asks, adds the forward `5201/both` open only to `CLIENT_IP`, prints the iperf3 commands for agent, server and client, takes the client's pasted summary lines into the report and removes the forward. | The report, plus the CPU and link of each host. |

## Reproducible performance procedure

Do not publish benchmark numbers without collecting them. On the same Linux host pair and with the same CPU allocation, run `iperf3` directly over the underlay and then over the WireGuard path for IPv4 and IPv6, TCP and UDP. Record the kernel, CPU, image digest, MTU, test duration, number of parallel streams, and tunnel state. Use a warm-up, then at least three measured runs for each case; repeat with three agents active. Report throughput, RTT/jitter/loss (UDP), CPU utilization, and any handshakes/retransmits. Verify the normal unmarked baseline separately so throughput changes are not mistaken for routing correctness.
