# RIFT architecture and security boundaries

RIFT uses one Rust binary, an agent-initiated WireGuard tunnel and a separate enrollment transport. Normal same-family application packets remain in Linux WireGuard, routing, conntrack and nftables. `ip` and `wg` are executed directly as maintained Netlink clients; no shell interprets configuration values. `nft` receives a generated atomic batch on standard input.

## Trust and exposure

The VPS operator controls all publications. Only the local Unix socket permits administration; socket permissions and Linux peer credentials restrict callers to root or the daemon UID. TCP 8443 speaks the bounded RIFT TLS enrollment protocol, not HTTP, and accepts no admin operations. TCP 8444 binds the VPS tunnel addresses and carries narrow agent requests inside WireGuard. Agents cannot request arbitrary routes, commands, firewall programs or publications.

An invitation contains a random one-time bearer credential and a public CA certificate. The latter enters the ordinary rustls root store; chain, hostname/IP SAN and time checks stay enabled. The server stores only the credential hash. Tokens are name-bound, expiring and reserved atomically to a durable agent identity, public key and attempt ID. Pending peers receive only access to activation/control, with no publication rights. Activation over WireGuard proves possession of the private key before consuming the token. Identical pending retries are idempotent; used tokens cannot enroll another installation.

The VPS is trusted by agents to deliver published traffic with external source addresses. An agent accepts those sources from its single VPS peer, but its firewall limits delivery to the granted service tuples. VPS peers accept only their individually assigned `/32` and `/128` sources, which prevents one agent from impersonating another agent's tunnel address. All peers, including staged peers, are denied general forwarding and access to other agents. Agent-originated bans are limited to that agent's active translated forward and a bounded TTL.

Private WireGuard keys stay in separate mode-0600 files. The server's private CA material stays on the VPS. Automatic TLS generation commits one mode-0600 bundle before materializing PEM files, allowing restart after partial writes. Keep volume backups private. The automatic server certificate is valid for one year; certificate maintenance is necessary before future enrollments after expiry. Existing WireGuard credentials do not depend on TLS certificate expiry when enrollment is disabled.

## Export, backup and moving a server

Settings and state leave the server in two forms. `rift export` is a versioned JSON document (agents, forwards, VPN devices with grants, and the host helper's sites) that refers to agents by name and holds no key, token or ID. `rift import` plans against the current snapshot in a pure step (agent mapping and filters, duplicate detection, port-overlap checks, replacement of unknown listen addresses), checks each planned item against the machine, writes everything that passed in one state transaction and reconciles once. Agents are never created by an import because they need their own enrollment. `rift backup` streams the state directory as `tar.gz` out of the container: `state.db` is copied with `VACUUM INTO` from one read transaction (a live WAL database is never copied as a file), the other files are written atomically, and the database copy is taken first so every key file it refers to is included. The host helper adds the site records and the manifest; `rift restore` verifies the archive, stops the server container, writes the state volume through a throwaway container and starts the server again. Nothing large is staged in the container's small `/tmp`.

A restored server may sit on other addresses. During every reconcile, forwards whose listen address is not in `public_ips` move to the first configured address of the same IP version unless that collides with another forward; the others stay out of the dataplane and `rift status` lists them. The agent keeps the WireGuard endpoint announced at enrollment, but a `RIFT_SERVER` host that differs from it replaces the host (not the port), so a server move with a raw address needs one `.env` edit per agent.

## Transparent packet path

The VPS DNATs an explicitly assigned public IP/protocol/port tuple to the selected agent's tunnel address and target port, without SNAT. A forward with `ingress = "local"` adds `iifname != "<uplink>"` for every NIC that owns a configured public address, so packets that arrive on that NIC are not DNATed. Packets from another interface, such as a reverse proxy on a Docker bridge, still match. A proxy installed on the VPS itself connects from the host, and its packets never pass prerouting; for local-ingress forwards an `output_nat` chain (nat hook output) translates them too, so Caddy or Nginx from the distribution reach the agent with the VPS address as source. The home service must accept connections to the agent tunnel address. `ingress` defaults to `public`, and older stored forwards without the field stay public. Local ingress is only valid for transparent mode. When UFW user chains exist, a local forward also accepts forwarding into `rift0` from interfaces other than the public uplink; the RIFT grant still drops anything that was not DNATed. The agent records a reserved connection-mark bit range for granted ingress. Locally generated replies restore that mark in a route-type OUTPUT chain; Docker replies restore it in PREROUTING before host routing. A dedicated routing table sends the reply back through WireGuard. Conntrack reverses Docker publication NAT and then the VPS DNAT.

Published TCP flows receive grant-scoped MSS clamping on SYN and SYN-ACK in the VPS and agent forwarding chains. The kernel uses the forward/reverse route MTU and only lowers an existing MSS. This accommodates Docker networks with a larger MTU than WireGuard. Each option update is separate from the grant's accept rule, so an absent MSS option does not prevent an otherwise allowed connection.

`host_firewall = "auto"` (the default) is the exception to the rule that RIFT only writes its own `inet rift` table. Another firewall can still drop a packet that `inet rift` accepts, because those are separate base chains. RIFT installs `rift-host-in` and `rift-host-fwd` and one commented jump at the start of the chain where that firewall decides: the UFW user chains when they exist, otherwise every foreign filter base chain hooked at input or forward that drops by policy or by a final plain `reject`/`drop` (Oracle Cloud images, Docker's forward policy, firewalld). These rules use only matches that `iptables` can read back, so `iptables -S` and `iptables-save` keep working on the tables it shares; in particular no `ct state` match, as replies-only is enforced in `inet rift`. The server jump accepts tunnel control, WireGuard UDP, enrollment TCP, and forwarding between each public-address NIC and `rift0`. The agent jump accepts granted input on its tunnel address and forwarding in or out of `rift0`. Flows that are not granted still hit the RIFT drop rules. `host_firewall = "off"` or `RIFT_HOST_FIREWALL=off` leaves those chains untouched.

The agent uses broad WireGuard AllowedIPs to accept external source addresses, but installs no general default route in its main table. Source rules for its own tunnel addresses also permit the first IPv6 reply lookup when no native IPv6 default exists. Unreachable fallback routes and egress guards stop marked replies from falling back to the home WAN. UDP applications bound to a wildcard address, IPv4 or IPv6, must bind their tunnel IP or select the received destination as their reply source; otherwise their replies leave through the home WAN. Backends published with Docker `-p` are not affected.

Explicit public listeners must be public unicast addresses listed in the VPS configuration. Backend addresses are always the selected agent's own assigned tunnel addresses, never arbitrary LAN prefixes. Existing interface-address and route overlaps are rejected. Port checks inspect local sockets and foreign NAT rules. Existing Docker/host firewall drops remain authoritative: an ACCEPT in RIFT cannot override a later DROP in another table. Fail2ban should restrict service bans to the inner service path; broad bans on the WireGuard UDP underlay can still interrupt the tunnel.

## Private VPN access

Roaming devices are additional WireGuard peers on the server's `rift0`, each restricted to its own `/32` from `vpn_pool`. The server forwards a device's packets back out `rift0` to the agent peer. Agents never see the device's key, only its VPN address and what it may reach. SQLite holds peers and grants in the same snapshot as agents and forwards; the private key stays in a mode-0600 file named after the public key's hash, outside the snapshot, status output and logs.

Enforcement has two layers. On the server, `inet rift` accepts only `device -> granted destination` in the forward chain, plus `ct state established,related` replies, before the existing `rift0` drops; devices are dropped on input (so they cannot reach the control port) and between each other. On the agent, input accepts only granted flows to its tunnel address (`server`, `full`, `port`), and forwarding accepts only granted flows to a named subnet. Masquerade is rendered only for grants with `--snat`, and only for that device and network. The `inet rift` DNAT path of public forwards is untouched; the VPN adds rules, it does not edit those.

A subnet grant also adds that network to the agent peer's AllowedIPs and a route through `rift0` on the server, so replies carrying LAN source addresses are accepted. The agent installs a route for the VPN pool only while it holds a subnet grant. Overlaps with host interfaces, host routes, RIFT pools and other agents' networks are rejected when the grant is created. Apply time re-checks the VPN pool and refuses to replace a foreign route for the same prefix, but does not re-scan host networks for every granted subnet, so a host network added later can collide until the grant is denied. Stale device and subnet routes are removed on every reconcile.

Revocation, disabling and denial remove the WireGuard peer, AllowedIPs, route and nft rules on the server in one reconcile; rollback after a failed apply never restores a revoked or disabled device or a withdrawn grant. Agents learn grants through the normal policy sync and fall back to deny for flows they do not know. An agent that is offline keeps its last rules, but the server no longer forwards.

Trust boundary: the agent identifies a device by its VPN source address, delivered by the server. A compromised server can forge any granted address, so agent-side rules protect against configuration mistakes and a stolen device key, not a hostile server. The agent does cap what a hostile server can ask for: it drops forwards and VPN grants outside its local `RIFT_AGENT_ALLOW_PORTS` and `RIFT_AGENT_ALLOW_SUBNETS` (subnet grants are refused unless listed) before applying or caching a policy, and reports the refusals as its last error. It also reports both lists with every sync; the server stores them on the agent record, warns when a new forward or grant falls outside them, shows such forwards as `refused` and leaves them out of the dataplane and the agent's policy. That view only drives warnings: enforcement stays on the agent (a refused internet exit is left out of the server's dataplane too). Stronger protection needs end-to-end authentication between device and agent. A device key alone gives access to exactly what that device is granted; there is no per-device second factor.

## Internet exit

A device has `server_exit: bool` (its main profile routes everything through the VPS) and `agent_exits: Vec<String>` (agent IDs; each is an extra profile that ends at that agent), stored on the device in the snapshot. All profiles of a device use the same key pair and addresses; only one is active on the phone at a time, and the VPS peer and each agent's `rift-exit` peer live on different hosts, so they do not collide. `vpn::client_config` renders the main profile, or with an agent ID that agent's profile (an error naming `rift vpn allow DEVICE AGENT exit` if the device has no exit via it). Devices are dual-stack: besides the `/32` from `vpn_pool` they hold a `/128` from `vpn_pool6`, both in the peer's AllowedIPs and as routes on the server. Grants stay IPv4. The first host of each VPN pool is reserved as the address of the agents' exit interface and never allocated.

**Exit through the server.** `vpn::server_rules` adds, for each enabled device with `server_exit` and after the isolation and grant rules, a forward accept from `rift0` to every other interface (excluding `vpn_pool`, `ipv4_pool`, the IPv6 pools and `169.254.0.0/16`/`fe80::/10` as destinations), an accept for `established,related` replies back, and a masquerade rule in a `postrouting_nat` chain. IPv6 follows only if `RIFT_PUBLIC_IPS` holds an IPv6 address; otherwise the device's IPv6 is dropped by an explicit rule. All of it sits before the final `rift0` drops, which remain in place. The input rule that drops devices on the VPS gains an IPv6 twin so IPv6 devices cannot reach the control port either. UFW gets `rift:exit` forward rules only while such a device exists.

**Exit through an agent.** Each agent that offers an exit (`RIFT_AGENT_ALLOW_EXIT`, part of its reported limits) creates a second WireGuard interface `rift-exit` with its own key in `exit.key` and reports public key, bound port and whether it has a global IPv6 address with every sync. The server assigns a UDP port from `exit_port_min`..`exit_port_max` per agent and keeps it. Before every reconcile `exit::sync` makes the snapshot hold exactly one managed forward (`Purpose::Exit`, transparent UDP) per listen address (first IPv4, first IPv6) for each active agent that at least one enabled device lists in `agent_exits`; this forward is persisted like any other so it gets a generation and the usual applied-generation handshake, shows in `list forwards`, and cannot be changed by hand. The agent passes it regardless of `RIFT_AGENT_ALLOW_PORTS` because `AgentLimits::refuse_forward` ties exit forwards to `RIFT_AGENT_ALLOW_EXIT` alone. The policy carries every enabled device that lists the agent (public key, IPv4, IPv6) and the gateway addresses; the agent configures them as peers with a host route each. The device's second tunnel is therefore end to end between device and agent, carried as UDP inside the agent's tunnel to the VPS; the VPS only DNATs it. Device configuration uses the same device key.

The agent's rules for `rift-exit` come before its `rift0` drops: devices may leave through any other interface with masquerade, but private, local and RIFT destinations are dropped (RFC 1918, `100.64.0.0/10`, link-local, loopback, multicast, ULA) unless inside `RIFT_AGENT_ALLOW_SUBNETS`, IPv6 is accepted only if the host has a global IPv6 address, replies return only as `established,related`, and `input` on `rift-exit` is dropped. The renderer always appends drops for `rift-exit` in all three chains, so a leftover interface is closed even if its rules failed to apply. A failure to apply the exit never holds back forwards or grants. The device's exit port, IPv6 reachability and MTU (server `mtu` minus 80) end up in the client configuration; `vpn::exit_problem` explains per agent why its profile is not available yet (agent refuses, has not reported its key, no port).

Trust: the agent applies the exit peers the server sends, so a hostile server could add a device of its own to the exit and use the agent's connection. That is why the exit is opt-in on the agent and why it cannot reach the agent's LAN unless the owner lists it.

## Web panel

The optional panel (`RIFT_WEBPANEL=true`) runs inside the server process and acts through the same admin requests as the CLI, behind an explicit action list that covers the CLI except printing the panel password. Reads (status, lists, log, diagnostics) are open to every logged-in session. Changes and secrets (invitation tokens, device configurations with private keys) additionally need a trusted connection: loopback without `Forwarded`/`X-Forwarded-*`/`X-Real-IP` headers, or an enabled VPN device with the panel flag, and `RIFT_WEBPANEL_CONTROL=private`. The proxy-header rule keeps a reverse proxy on the same host, whose connections also come from loopback, from making Internet clients trusted; a proxy that sends none of these headers defeats it. Over the public path the panel is read-only by design, so a password sniffed from plain HTTP does not allow changes.

Login takes the password and, once `webpanel.totp` exists in the state directory, a one-time code (TOTP, `src/totp.rs`). The server keeps a code's step as used, so a code works once; ten failed logins in a row lock all logins for 15 minutes. A secret that is shown but not confirmed exists only in memory. The CLI and the panel share this state in one object, and deleting or disabling the secret ends all sessions. With `RIFT_WEBPANEL_2FA=required` the panel refuses logins until a secret exists, and only `rift panel 2fa reset` on the server removes it.

Access is checked in three places. The listener set depends on `RIFT_WEBPANEL_ACCESS`: `private` binds loopback and the server's IPv4 tunnel address only, `public` binds every address. Each connection's source must be loopback, an enabled VPN device with the panel flag, or inside `RIFT_WEBPANEL_ALLOW`; in public mode an empty allow list admits everyone. On `rift0`, `inet rift` accepts the panel port only from those devices and from allow-listed tunnel sources, ahead of the rule that drops VPN devices on input; agents and other devices still hit the final drop. A device with the panel flag gets the server tunnel address in its AllowedIPs and nothing else beyond its agent grants.

Sites need the host (root, Docker, the reverse proxy's files), so the panel reaches them through a queue instead of widening the container. The server container mounts `/var/lib/rift-site` read-only, from which `src/sites.rs` lists the helper's records and the state of their forwards, and `/var/lib/rift-site-queue` read-write. A site change from a trusted connection is validated in Rust (agent name, domain, port, proxy; at most 20 pending) and written as one JSON file holding only those parameters. `rift-site-queue.path` (`PathExistsGlob` on request files) starts `rift-site-queue.service`, a oneshot running `rift-site process-queue` as root. It treats the file as untrusted: it opens it without following links, caps its size, accepts only `add`, `remove`, `export`, `import` and `backup` with exactly their keys and re-validates every value before calling the same code as the CLI (`command_add`, `command_rm`, `export_file`, `run_import`, `write_backup`). It writes `<id>.result.json` (`ok`, output or error), always deletes the request so the path unit settles, and removes results after a day. Export, import report and backup are left as `<id>.data` (0600) and removed after 15 minutes if the panel does not fetch them. The panel polls `site_result`, a read-only action that takes only a 32-character hex id, and `host_file`, which needs a trusted connection, hands the file out once and deletes it. A backup request needs the panel password and, with two-factor login, a fresh code again. The container can therefore queue validated site changes and the CLI's export, import and backup, and nothing else; export and backup hand it nothing it does not already hold (its own state and the read-only site records).

Authentication is a single password (environment or a generated mode-0600 file in the state directory). Logins are serialised with a one-second penalty for a wrong password. Sessions are random 256-bit tokens in an `HttpOnly`, `SameSite=Strict` cookie, held in memory for 12 hours. State-changing requests also need a custom header, which a cross-site page cannot send without a CORS preflight the panel never answers. Responses carry a strict Content-Security-Policy; the page loads no external resources. The server speaks plain HTTP: confidentiality comes from loopback, an SSH tunnel or WireGuard in private mode, and only from a TLS proxy in public mode.

## Terminal UI

`rift` without a command, or `rift tui`, on a terminal runs the terminal UI (`src/tui/`, ratatui with crossterm) in the RIFT container; the host command starts it with `docker exec -it`. It is a client of the admin socket like every other CLI command: it holds no state of its own and needs no listener, so it adds no network surface and no trust boundary. Whoever can run it could run any `rift` command already. Reads (status, device list, panel and two-factor state, the log) are fetched every three seconds in the background; changes are the same admin requests the CLI sends, and their results are rendered with the CLI's own messages (`src/output.rs`). Sites, exports, backups and imports go through the web panel's host queue (`crate::sites`), so the UI never writes host files. An export or backup request with `"keep": true` makes the host service save the file in `/var/lib/rift-site/files` (mode 0700, the newest 20 of each kind kept, so queued requests cannot fill the disk) instead of handing it back; the container reads that directory read-only to list the files and to read an export it imports. The container gains nothing from this: a backup holds keys the server already has. The health tab runs `rift --json doctor`, and the `:` prompt runs the binary itself with the given arguments, refusing the daemon commands and the host commands. The UI does not log to the terminal it draws on. `RIFT_TUI=false` only stops `rift` alone from opening it.
## Enrollment port

`enrollment` (`RIFT_ENROLLMENT`) is `auto`, `always` or `off`. In `auto` (the default) every reconcile opens the enrollment listener when an invitation is unconsumed and unexpired, and closes it otherwise; the invitation is consumed when the agent activates over the tunnel, so an agent whose enrollment response was lost can still retry until then. Invitations, cancellations, activation and agent removal reconcile at once; expiry is noticed by the periodic reconcile. RIFT's UFW accept for the port follows the listener. When the bind address is `0.0.0.0`, the server adds an IPv6-only listener on the same port (if the host has IPv6), so agents with only IPv6 can enroll; UFW opens the port in both families. RIFT does not change cloud firewalls.

## Configuration and recovery

TOML and documented environment overrides own static deployment settings. SQLite owns agents, invitations, bans and dynamic forward grants; TOML reload never replaces those rows. CLI changes commit desired state transactionally. The operation journal and separately confirmed snapshot distinguish requested configuration from successfully reconciled kernel configuration. New publications wait for the agent's generation ACK. `status` reports pending forwards and apply failures.

Configuration cannot commit atomically across SQLite, routes, WireGuard and nftables. The reconciler serializes kernel changes, retries desired state after failures and attempts to restore confirmed grants. Rollback never restores a removed/disabled peer, a revoked forward or a superseded key. If an underlying kernel operation also prevents rollback, the failure remains visible; this is not an unconditional cross-system transaction guarantee. A process restart reconstructs desired state and the agent restores its cached policy before opening control.

Stored state has a format number: SQLite's `user_version` for `state.db`, `version` in an agent's `identity.json`. On start, RIFT migrates an older format step by step in one transaction, after copying the database to `state-before-vN-TIME.db` (mode 0600) next to it; a format from a newer RIFT is refused, since a downgrade cannot know what it would lose. A database written before formats were numbered (builds before 1.0) is format 1. Every change to what is stored adds a migration in `src/state.rs` and a test against a fixture of the previous format (`tests/fixtures/`); a test fails when a format has no migration to the next. An agent's cached policy is not migrated: the server sends it with every sync, so an unreadable cache is dropped.

Live reload permits validated mutable parameters; interfaces, address pools, routing reservations, listener ports and TLS identity require a service restart. On an orderly stop the daemon removes its owned networking state; restart reconstructs it from persistent state. A forced kill, crash or cleanup failure can leave networking state behind. If the state volume is gone, startup replaces an interface whose alias still starts with `rift:`, replaces an existing `inet rift` table, and replaces routes and policy rules in the reserved table when every remaining entry is one RIFT itself installs. An interface without that alias, or any other route or rule at those priorities, is still refused. Deleting a state volume first is not an uninstall procedure.

## Explicit translation

Cross-family translation is an opt-in TCP/UDP forwarder in the same binary. Its application packets traverse userspace and the target sees the VPS tunnel address. Original remote addresses are recorded in structured VPS logs and can be blocked per forward through the VPS or agent's local CLI. Connection/session counts and UDP queue sizes are bounded. Transparent same-family forwards do not enter this code path.

## Evidence boundary

Unit tests, real loopback TLS tests, and IPv4/IPv6 translation tests can run on a developer machine. They do not prove transparent kernel forwarding, Fail2ban, Docker publication or production SSH continuity. The Linux namespace and Docker integration suites exercise those paths on disposable privileged runners. SFTP, Traefik, full host reboots, staging firewall combinations, a real cloud NAT (the namespace suite simulates one) and iperf3 measurements remain explicit release gates until their real results are recorded.
