# Changelog

All notable changes are listed here. Versions follow [Semantic Versioning](https://semver.org/). Within a major version, configuration settings keep their meaning, stored state is migrated on update (after a copy of the old state is kept), and a server serves agents of its own and of the previous release. Update the server first, then the agents.

## [Unreleased]

### Web panel

- The panel is laid out like the terminal UI: tabs for the overview (stat cards, a live traffic graph, the agents, what needs attention, the latest log), agents (open invitations as rows with their time left; new token, cancel), forwards (filter and sort as in `rift list forwards`), VPN devices, sites (with the proxy `rift proxy` shows), bans, the panel itself (whether it runs, two-factor login, devices with access), the log (follow, level, text filter), health and backup. A table with the selected row's details beside it, the row's actions in a bar at the bottom and on right click, an agent focus, and keys (`1`–`0`, `/`, `F`, letters, `?`). It works on phones and in light and dark mode, still without any external resource. The invitation dialog copies the whole setup, the join line or the `.env` lines; renaming an agent says that its `.internal` name follows.
- The overview the panel loads also carries what each agent allows (`RIFT_AGENT_ALLOW_*`), its public key, the WireGuard byte counters (not the endpoints) and the RIFT version.

### Terminal UI

- `rift` without a command opens a full-screen terminal UI on the server and on agents (`rift tui` does too). It covers what the CLI and the web panel do: an overview with live traffic and what needs attention; agents with invitations, enable/disable, rename, key rotation and names; forwards (add in the short form, enable/disable, ban, remove); VPN devices with grants, withdrawals, exits, DNS, names, panel access and their WireGuard configuration as a QR code; sites through the panel's host queue; bans; the web panel's password and two-factor login; the log with follow, text and level filters; and `rift doctor`. It works by keyboard and mouse (tabs, rows, buttons, form fields, wheel, right click and double click for the actions of a row), and `:` runs any `rift` command inside it. It talks to the daemon over the same admin socket as the CLI and shows the same messages.
- `RIFT_TUI` (default `true`) in the server and agent `.env` turns it off: `rift` alone then prints the help, as before. `deploy/setup-server` and `deploy/join` ask for it and take `--tui`/`--no-tui`. The commands are unaffected either way.
- The Backup tab exports the settings, saves a backup with every key and imports an export file (dry run first, with `OLD=NEW` agent names). The UI cannot write host files, so the web panel's host service saves exports and backups in `/var/lib/rift-site/files` (created by `deploy/install-cli`, mode 0700; the newest 20 of each kind are kept) when a queued request carries `"keep": true`; files to import go there too. An older host helper refuses such requests; the UI then says to run `deploy/install-cli` again. The Sites tab names the proxy `rift proxy` shows.
- QR codes in the UI leave out the configuration's comment and blank lines and use error correction level L: a typical main profile takes 33 rows instead of 39, an exit profile 33 instead of 47. Windows too small for the dialog show the code alone on the screen. Narrow tables leave out their least important columns, and the Forwards tab shows the selected forward in full below the table.
- Open invitations appear on the Agents tab as rows of their own, with how long the token is valid, until the agent enrolls; `t` replaces the invitation with a new token, `c` cancels it. The invitation dialog copies the whole setup (`git clone`, `cd RIFT`, `deploy/join`), only the `deploy/join` line, or the three `.env` lines.
- `/` filters the Forwards, Agents, VPN devices, Sites and Bans tabs, `s` sorts the forwards by ID, agent, port or state, and `F` focuses on one agent: forwards, devices, sites and bans then show only what concerns it.
- When `rift` alone prints the help, or `rift tui` finds no terminal, the message names the usual cause: a host command older than the image (`sudo sh deploy/install-cli`).
- After adding a VPN device, the terminal UI says what to do next in its own keys (g grants access, c shows the configuration) instead of the CLI's commands, and no longer asks to import again the configuration of a device that was just created. Enter submits a dialog from any field; Space ticks a box (Enter used to tick it, so Space then Enter undid the choice).
- The host command `rift` starts the container command with a terminal (`docker exec -it`, passing `TERM` and `COLORTERM`) when it is called without a command, or with `tui`, on a terminal.

### Names for VPN devices

- The suffix of the agents' names is configurable: `RIFT_NAMES_SUFFIX` (default `internal`). `home.arpa` is reserved for home networks like `internal` and, unlike it, on the Public Suffix List, which browsers use to tell addresses from searches (Safari searches for `core.internal`). Any domain name is accepted, a subdomain of your own too (`home.example.net`, no DNS record needed); the README says which ones suit. RIFT answers only the agents' names under the suffix and passes every other name on, so the public names of your domain keep working while the tunnel is on. `deploy/setup-server` asks for it. Devices import nothing new when it changes.

### Commands

- `rift host allow AGENT TARGET...` lets the VPS host itself reach an agent's tunnel address, for example `rift host allow node1 22/tcp` and then `ssh USER@10.13.0.2` on the VPS: no public port, no VPN device. Targets are ports and ranges, `server` and `full`; `rift host deny AGENT [TARGET...]` withdraws them and `rift host list` lists them. The agent applies them as grants from the server's tunnel address, within `RIFT_AGENT_ALLOW_PORTS`; refused ones show in `rift status`, `rift doctor`, the attention lists of the web panel and the terminal UI, and in the agent's log as access of the server host. The Agents tab of both lists them in an agent's details and adds or withdraws them with `h` ("Server access"; `H` withdraws in the terminal UI). Export and import carry them. The policy an agent receives keeps its format: a host grant reaches it as a VPN rule whose source is the server. Before, an agent dropped every connection from the VPS host that no forward covered; a forward with `--ingress local` was the only way in.
- `rift list forwards` takes filter words and options: `rift list forwards nas 8080`, `--agent NAME` (repeatable), `--port N` (inside ranges too), `--protocol tcp|udp`, `--sort id|agent|port|state`; `agent:NAME`, `port:N`, `proto:tcp` and `state:WORD` as words. `rift list agents`, `list devices`, `list bans` and `list sites` take filter words, and all but agents `--agent NAME`; for devices that means a grant on the agent or an exit through it. `--json` gives the filtered list.

### Setup

- `deploy/setup-server` checks whether another program listens on the web panel port or the enrollment port (TCP; RIFT's own listeners do not count), names it and offers the next free port as the default, opening the question group for it. An explicit `--set` of a taken port is refused with the same message.
- `deploy/join`, `deploy/setup-server`, `deploy/setup-proxy` and `deploy/publish-panel` give `.env` to the user who ran them with `sudo` (mode 0600 as before), so that user's `docker compose` reads it without `sudo`. Before, every run left it owned by root, and an agent host needed `sudo docker compose` after `deploy/join`. Run as root without `sudo`, the file keeps its owner. The temporary copy written on the way is no longer readable by others for a moment.
- `deploy/setup-server` asks for every setting of the server `.env` (image version, ports and enrollment, tunnel and VPN pools, VPN DNS, every web panel setting including the password and two-factor login, the reverse proxy with its Let's Encrypt settings and the panel route of `deploy/publish-panel`; besides a proxy in Docker, `own` takes over a proxy that already runs on the server: it detects what holds port 443, asks what `rift add site` needs for it, such as the Caddy container and site directory or the Nginx Proxy Manager login, and sets it with `rift proxy`), in the order of `.env.server.example`. Rarely changed groups are asked only after a yes. Defaults come from the existing `.env`, so running it again changes settings in place; values are checked before anything is written; `--set KEY=VALUE`, `--version` and `--publish-panel` set them without questions. A setting at RIFT's default stays a comment in `.env`, and `RIFT_ALLOW_PRIVATE_LISTENERS` is reset when the address is no longer private.
- `deploy/join` also asks for the agent's limits (`RIFT_AGENT_ALLOW_PORTS`, `RIFT_AGENT_ALLOW_SUBNETS` with the LAN networks it finds, `RIFT_AGENT_ALLOW_EXIT`) and the image version, asks for a missing server, name or token, and changes the settings of an enrolled agent when run again without a token. Options: `--allow-ports`, `--allow-subnets`, `--exit`/`--no-exit`, `--version`, `--set KEY=VALUE`, `--yes`.
- `deploy/publish-panel DOMAIN --read-only` publishes the panel read-only: logins work through the domain, changes and secrets stay on the VPS, SSH tunnels and panel VPN devices (`RIFT_WEBPANEL_CONTROL=private`). `deploy/setup-server` asks for a panel domain only after a yes and then whether changes are allowed there, read-only by default; before, it always allowed changes and overrode the answer to "Changes allowed from".
- `deploy/publish-panel` trusts the Docker network a proxy container actually reaches the panel from (asked with `ip route get` in its network namespace) instead of requiring `10.255.13.0/24`, so a proxy of your own in any Docker network works without settings; `--off` removes that network again. It no longer needs Python for this check, which also looked only at the container's first network.
- `rift proxy caddy --host` points the site commands back at a Caddy on the host. When Caddy moves between host and container or to another site directory, `rift proxy caddy` now moves the files of its sites and panel route along, reloads the new Caddy and removes the old files (nothing changes if the new Caddy cannot be reloaded). Before, a move left the sites in the old directory, and there was no way back from a container to the host.
- `rift add agent` prints the invitation as one block in order: `git clone`, `cd RIFT` and the `deploy/join` line, then the three `.env` lines for a manual setup, with how long the invitation is valid. Before, its hints went to stderr, and `docker exec` behind the host command printed them all before the commands. The web panel shows the clone step separately as well.
- `deploy/join` refuses a machine that runs `rift-server`, and `deploy/setup-server` one that runs `rift-agent`: both share the compose project, the state volume and the host network. Before, only an existing `.env` of the other role was noticed, not a deleted or second checkout. While it waits for the server to accept the agent, `deploy/join` prints the agent's latest message every 10 seconds instead of staying silent for up to two minutes.
- An apply error in `rift status` and the error of an admin command now include their cause, such as the message of a rejected nft batch, instead of only the outermost step ("atomically install RIFT nftables table"). `rift add site` no longer prints "rift: rift:".
- `deploy/join` reports success only once the agent has a WireGuard handshake with the server (`"connected"` in `rift --json status` on the agent), not already when its identity is marked active. Without a handshake it names the two causes: an identity from a server that was set up again, or a closed UDP port.
- An enrolled agent that gets `RIFT_ENROLLMENT_TOKEN` of another server (one set up again) stops with a message naming `docker compose down -v`, instead of ignoring the token and dialling the old server. The agent stores the fingerprint of its server's enrollment CA for this; agents enrolled before only log a warning.
- `.env.server.example` and `.env.agent.example` are grouped into sections in the order of the scripts; commented lines show RIFT's defaults.

### Fixes

- A VPN grant the agent refuses (outside `RIFT_AGENT_ALLOW_PORTS` or `RIFT_AGENT_ALLOW_SUBNETS`, for example after removing a port from the agent's `.env`) showed only in the device's details. The VPN devices tab now marks it in the GRANTS column (`2 ✗1`) of the terminal UI and in the Access column of the web panel, and `rift status`, `rift doctor`, the overview's attention list and the panel's name it with the reason.
- Examples in empty form fields read as values to type ("none, or e.g. …" was taken for the word none): optional fields now say "optional, e.g. …" or "empty for everyone, or e.g. …".
- VPN devices could not reach a service that Docker publishes on the agent's tunnel address (`ports: "10.13.0.3:3000:3000"`), although they had a grant on the port: Docker rewrites the destination to the container before RIFT's rules see the packet, so it is forwarded instead of arriving at the host, and RIFT's agent rules allowed grants only for the host itself and dropped it. Grants on an agent now match the connection as the device opened it (its original destination in conntrack) for the host and for forwarded packets, and mark it like a forward, so that the container's answers, which come from its own address, go back through the tunnel instead of to the LAN gateway. Published ports work like services on the host. A container port that is not published, or not granted, stays unreachable.
- VPN devices that use RIFT's names (`NAME.internal`) resolved nothing on a server whose host firewall drops by default (Oracle Cloud images, UFW): their DNS goes to port 53 of the server's tunnel address and is redirected to the name server's port 53053, which the host firewall integration did not open. It now opens that port on the tunnel interface, for the server's tunnel address only. `rift doctor` reports whether the name server answers once a device uses names, and the server logs a warning when it cannot listen for 30 seconds. The port is configurable as `RIFT_NAMES_PORT` (default 53053), and `deploy/setup-server` checks it like the panel and enrollment ports, for TCP and UDP.
- A web panel whose port another program holds no longer fails silently. Before, the server logged one line and ran without it, while `rift panel status` and the terminal UI showed it as on, and `rift doctor` reported it as answering because the other program answered. Now `rift panel status`, `rift doctor` and the terminal UI (Web panel tab, Overview) say that it is not running, why, and how to find the program (`sudo ss -ltnp 'sport = :PORT'`); the server tries the port again every 30 seconds and starts the panel once it is free.
- Websites (`rift add site`) failed with the nftables 1.0.6 of the image: the output NAT chain of local-ingress forwards used the priority name `dstnat`, which nftables before 1.0.7 accepts only on the prerouting hook, so the server rejected the whole configuration ("invalid priority expression value in this context") and kept the previous one. The chain now uses the number -100.

## [1.0.0]

First release. RIFT publishes services of home servers behind NAT or CGNAT through a VPS: the home server (agent) dials the VPS (server) over WireGuard, and the server forwards public ports to it or lets private VPN devices reach it. See the [README](https://github.com/weneten/RIFT/blob/v1.0.0/README.md) for setup and the [test matrix](https://github.com/weneten/RIFT/blob/v1.0.0/docs/deploy.md#functional-test-matrix) for what is tested and what is not.

### Setup

- `sudo sh deploy/setup-server` sets up the server in one step: it asks for the public address, the endpoint agents dial and the web panel (with detected defaults, or `--endpoint`, `--public-ips`, `--panel`/`--no-panel`, `--yes`), recognises a cloud NAT, prepares the host, writes the configuration, installs the `rift` command and waits until the server is ready.
- `rift add agent NAME` creates a single-use, expiring, TLS-pinned invitation and prints `sudo sh deploy/join SERVER NAME TOKEN`, which sets up the agent in one step and removes the used token from `.env` afterwards. Inviting an existing name again moves the agent to a reinstalled host and keeps its addresses, forwards and grants.
- Host scripts: `deploy/prepare-host` (sysctls, WireGuard check; also in Proxmox LXC containers), `deploy/install-cli`, `deploy/uninstall-host`, and `deploy/field-check`, which collects a report without secrets about a host and checks that RIFT comes back alone after a reboot.
- Docker image for `linux/amd64` and `linux/arm64`; `RIFT_VERSION` in `.env` pins a release. The image contains the licenses of RIFT, of the Rust crates in the binary and a list of its Debian packages (see `NOTICE`).

### Forwards and sites

- TCP and UDP forwards from the server's public addresses to an agent (`rift add forward`): transparent, so the service sees the client's own address, or translated between IPv4 and IPv6.
- `--allow-from ADDRESS[,NETWORK...]` limits a forward to the named clients.
- Time-limited client bans on translated forwards: `rift add ban FORWARD_ID IP [--ttl 1h]`.
- HTTPS sites through Traefik, Caddy, Nginx or Nginx Proxy Manager on the VPS (`rift add site`), optionally limited with `--allow-from`. `sudo sh deploy/setup-proxy traefik|caddy|npm` sets up Traefik, Caddy or Nginx Proxy Manager in Docker the way `rift add site` expects it, on any distribution, and `deploy/setup-server` offers it. With `--migrate` it switches from one of them to another: it stops the old one, sets up the new one and moves every site (the forwards stay), or starts the old one again if the new one cannot be set up. Caddy in a container is reloaded there (`rift proxy caddy --container NAME --sites-dir DIR`). A proxy installed on the VPS itself, such as Caddy or Nginx from the distribution, reaches local-ingress forwards too. `rift remove site` says what it removed; `rift list forwards` shows which site a forward belongs to.

### Private VPN access

- VPN devices that reach chosen ports, hosts or networks behind an agent without a public port: `rift vpn connect DEVICE AGENT TARGET...` creates the device, grants the targets and prints the QR code; `rift vpn allow`/`deny` change grants later.
- Every change says which devices must import their configuration again; another port on an agent a device already reaches needs none. A grant that the agent's own limits (`RIFT_AGENT_ALLOW_*`) refuse is reported as stored but not reachable.
- DNS through an agent (`rift vpn dns`) and internet exits through the server or an agent.
- Names: `rift vpn names agent NAME on` lets every device with a grant on the agent reach it as `NAME.internal`. The server answers these names only for agents a device has a grant on and passes other lookups to the device's DNS agent, with the device's address as EDNS Client Subnet, or to `RIFT_VPN_DNS`. `rift vpn names device NAME off` keeps a device out.

### Operation

- Web panel with password and optional two-factor login, reachable over the VPN (`rift panel connect`) or, behind a TLS proxy, publicly; a public panel takes the password over HTTPS only. For networks that block WireGuard's UDP, `sudo sh deploy/publish-panel DOMAIN` puts the panel behind the proxy of `deploy/setup-proxy` at `https://DOMAIN` and allows changes there (`RIFT_WEBPANEL_CONTROL=public`); the panel port stays off the internet. Two-factor login is strongly advised then; without it the server and the panel warn. It manages agents, forwards, sites, bans, VPN devices, exits and names, exports and imports settings (with a preview before anything changes) and downloads a backup after asking for the password and code again; restore stays on the CLI.
- `rift status`, `rift doctor`, `rift list ...` and `--json` output; `rift list agents` shows each agent's RIFT version and `rift status` names agents older than the server.
- `rift backup` and `rift restore` for the server state; `rift export` and `rift import` move forwards, sites, devices, grants and names to another server. The web panel offers export, import and backup through the same code on the host.
- Stored state and the agent identity carry a format number and are migrated on update, after a copy of the old state is kept; state from a newer RIFT is refused. State written by builds before 1.0 is migrated as well.
- The agent's own limits (`RIFT_AGENT_ALLOW_PORTS`, `RIFT_AGENT_ALLOW_SUBNETS`, `RIFT_AGENT_ALLOW_EXIT`) bound what the server can open on it.
- Security reports go through GitHub's private vulnerability reporting (`SECURITY.md`).
